## 背景（なぜ新規 fix か）

feedback（前 iter = VALUABLE）の bullet 3 は「ChunkerConfig 以外にも指紋に入っていない境界/内容ノブの全系監査」を要請した。TASK-0217 はその命名記号（`heavy_model`/`ChunkerConfig`/`chunker`）が本 checkout で grep-proven PHANTOM と確定したが、**「同じ content-hash keying の下で stale になるノブ」という問い自体**は実在する content-hash keying 全てに適用すべきだった。本 TASK は cache 以外の content-hash keying を自前で列挙し、真の gap を発見した。

### 発見: resume-ledger `_config_fingerprint` は第2の content-hash keying

`scripts/run_freeze_validloss_ci_9b.py` の resume-ledger `_config_fingerprint`（line 1007）は、full-budget §4 run の resume 性を担保する run-config identity。docstring 自身が「`lora_r`(4ad9a73)/`learning_rate`(d6af3cd)/`max_dataset_rows` を『silent-replay → corrupt-but-green §4 verdict(GOAL §7)』クラスの gap として順次閉鎖した」と記録する。cache とは別の content-hash keying で、**`load_ledger` は header fingerprint が完全一致する arm のみ再生**する（line 1195 `stored == fingerprint`）。

### gap: model 量子化ノブが fingerprint に無い

`ModelConfig`（`src/training/config_schema.py:44`）は `name_or_path`/`dtype`/`load_in_4bit`/`bnb_4bit_quant_type`/`bnb_4bit_compute_dtype` を持ち、`load_base_model`（`src/model/load_model.py:35-215`）は後者 4 つ全てを `BitsAndBytesConfig`/`torch_dtype` に流し込み **model の forward/backward 数値精度を決定**する。これは全 arm の `valid_loss` を変える。しかし `_config_fingerprint` は `model`（= `name_or_path` のみ）を取り、量子化 4 ノブを含まない。

→ 同じ model 名（例: `Qwen/Qwen3.5-9B`）で量子化だけ変えた再実行（`nf4`→`fp4`、4bit↔full bf16、compute_dtype 変更）は **arm 結果が変わるのに fingerprint が完全一致** → `load_ledger` が旧量子化の arm を silent replay → corrupt-but-green §4 verdict。`lora_r`/`learning_rate`/`max_dataset_rows` と**同一 silent-replay クラス**。cache 側は `test_different_load_in_4bit_*`/`_dtype`/`_bnb_4bit_quant_type` で保護済みだが ledger 側は未保護の**非対称**だった。
