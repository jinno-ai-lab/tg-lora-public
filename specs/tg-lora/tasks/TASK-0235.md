## 決定論（なぜ producer-driven L3 が必要か）

証跡は 3 つの独立な attack を 1 つの producer-driven E2E callgraph で prove する:

1. **Producer-leaf drift attack.** `scripts/run_freeze_validloss_ci_9b.py` 行 164-166 は
   `from src.tg_lora.freeze_evidence_hash import EVIDENCE_HASH_KEYS as EVIDENCE_HASH_KEYS, evidence_hash as _evidence_hash`
   で leaf を import するが、将来「producer 側の `_evidence_hash` をローカルに再定義」「`EVIDENCE_HASH_KEYS` を
   producer 側で extend」するリファクタが入ると leaf import は維持されたまま producer 内の hash 出力が drift する。
   leaf 単独 pin では捕捉不可。producer-driven E2E でのみ捕捉可能（deposit の stamped hash が leaf の
   `evidence_hash` 関数と **byte-identical** であることを real bytes で確認）。

2. **Stamp-only-no-verify attack.** producer が hash を stamp しても replay 側が同じ hash を再導出しなければ
   `not evidence_hash_stale` conjunct が無意味になる。両方向の整合
   （stamped == leaf(deposit)、replay_derived == leaf(deposit)）を 1 つの test 内で固定。

3. **Consumer-leaf drift attack.** `scripts/section4_operator_decision.py` 行 76 で
   `from src.tg_lora.freeze_evidence_hash import evidence_hash` 経由で leaf を import している。
   replay 側の `_evidence_hash_stale` 関数が `stored_hash != evidence_hash(data)` 比較する際、
   もし replay 内に独自 canonicalization が入ると leaf と drift し、tampered deposit が
   検出されなくなる。producer-driven E2E + replay-driven E2E の両軸で leaf 同一性を pin。

## 変更（test 1 file のみ・src/・scripts/・既存 fixture 全て無変更）

### `tests/test_evidence_hash_chain_integration.py`（新規）

producer (`run_ci_9b`) + replay (`replay_samples`) + leaf (`evidence_hash`) + decision (`arc_complete`) の
**完全鎖** を 1 つの test class 内で mutation-proven する。積極枝:

- **Case 1 (happy path):** 既存の `_cpu_cfg` + `_tiny_llama` + `_CharTokenizer` で `run_ci_9b(architecture="homogeneous")` を実走
  → `result_to_json` → `_write_deposit(tmp_path / deposit.json)` → 既存の `load_samples` + `replay_samples` で再判定
  → deposit の `evidence_hash` フィールドが leaf `evidence_hash(deposit)` と **byte-identical** であること、
  `replay` 経由で `evidence_hash_stale=False` になること、`section4_operator_decision._assess_leg` 経由で
  `arc_complete=True` になることを検証。

- **Case 2 (coordinated repaint detection):** Case 1 の deposit を読み込み、`candidate_losses` 配列の 1 要素を
  +0.01 改ざん → 再保存 → `replay_samples` → `evidence_hash_stale=True` 確認 → `_assess_leg` 経由で
  `arc_complete=False` 確認。`evidence_hash_stale` 検出が real bytes で動作することの proof。

- **Case 3 (derived label repaint doesn't salvage):** Case 1 の deposit の `verdict` フィールドを
  `"SURPASSES"` に上書き（derived label 改ざん）→ 再保存 → `faithful` 検出 + `evidence_hash_stale=False`
  （hash は derived label 含まない）→ `citable_as_full_section4_verdict=False` 確認。
  「faithful は manipulated verdict を捕まえる、hash は捕まえない、しかし両者は gate の異なる landmark であり
  共に必要」という threat model の proof。

- **Case 4 (producer-leaf import identity):** producer の `EVIDENCE_HASH_KEYS`, `_evidence_hash` が
  leaf の `EVIDENCE_HASH_KEYS`, `evidence_hash` と同一オブジェクトであることを `is` で pin。
  producer が leaf を import しているか rebind していないかを assertion で固定。
  これで「producer 側で独自 canonicalization を reintroduce する」リファクタを即時 RED 化。

- **Case 5 (replay-leaf import identity):** replay (`scripts.replay_freeze_validloss_ci`) の
  `evidence_hash` 名前空間が leaf の `evidence_hash` 関数と同一オブジェクトであることを `is` で pin。
  replay 側で独自 hash 実装が reintroduce されないことを固定。

- **Case 6 (end-to-end operator decision):** Case 1 (happy) と Case 2 (repaint) の deposit を
  `section4_operator_decision` の `_assess_leg` を実走 → `arc_complete` happy vs repaint の binary
  対比で「`not evidence_hash_stale` conjunct が arc_complete gate の最後の砦として機能している」ことを
  E2E で prove。`test_section4_operator_decision.py` の pre-built tampered deposit は静的テストだが、
  本 test は **producer が生成した real bytes** に対して同じ conjunct が機能することを示す。

積極枝は L3 統合 test 6 件 + leaf identity test 4 件、`pytest` 標準 assertion のみ、stub 不要
（既存の `test_freeze_ci_9b_launch_honesty.py` の `_cpu_cfg` / `_tiny_llama` / `_CharTokenizer` 相当を
本 test 内で再利用）。**GPU 不要** — 全 test が CPU 上で完結。`test_freeze_ci_9b_launch_honesty.py` と同じく
src.data 非依存。

mutation 検証:
- Case 2 で `candidate_losses` 改ざん → Case 1 PASS / Case 2 RED。stale 検出が実動作。
- Case 4 / Case 5 の `is` 比較 → producer/replay の local rebind で即 RED。leaf-single-source-of-truth pin。
- Case 6 で `arc_complete` 計算式から `not evidence_hash_stale` conjunct を一時的に抜く → Case 6 RED。
  6b628fe で追加された conjunct が upstream caller まで確実に届いている proof。
