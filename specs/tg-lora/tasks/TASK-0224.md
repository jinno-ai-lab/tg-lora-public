## 動機（feedback bullet 3 への実装応答）

feedback bullet 3: 「context_size を label-affecting とする判断は入力切 truncation が
ラベルを変えるという根拠に依存する → 統合テストで同一入力の設定差による cache miss と
再推論を確認せよ」。`context_size` は本 checkout では grep 0 hit の phantom 語で、実体は
`max_seq_len`（追記24 確認済）。既存の統合証明（TC-132-09）は **cache path 乖離 +
source='built'（rebuild 分岐が走った）まで**しか pin していなかった:

1. **bytes 水準の未証明**: 再推論が実際に設定を反映した bytes を生成したか（永続化
   artifact の内容差）はどの test も検証していなかった。
2. **逆方向の未保護**: 既存ガードは「byte を変える全 config field が指紋に**入っている**」
   （field 列挙・`TestCacheFingerprintCompleteness`）を pin するが、「指紋の下に保存される
   bytes が指紋と**矛盾しない**」は pin していなかった。loader が truncation を忘れた
   producer は、指紋の `max_seq_len` より**長い** rows を永続化でき、後の正しく truncate
   された run（同一 cfg → 同一指紋 → 同一 cache path）がそれを silent に replay する =
   TASK-0206/0207 の silent-replay class が指紋側でなく **producer 側から**到達する。
